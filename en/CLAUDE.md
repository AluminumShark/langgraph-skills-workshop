# From LangGraph to Skills: Collaboration Rules (English edition)

An NTU AI Club workshop for beginners who have just learned Python. Two 120-minute sessions.
Session 1: 2026-11-09. Session 2: 2026-11-16.
Public repo: AluminumShark/langgraph-skills-workshop.

This file covers the `en/` tree. Run every command from the repo root.

## Relationship to the Chinese edition

- The Chinese files at the repo root are the primary source. `en/` is a translation that mirrors them.
- When a Chinese source changes, update the matching `en/` file using [GLOSSARY.md](GLOSSARY.md). When a new cross-file name appears (an identifier, a protocol string, a slide title, a sample value), add it to the glossary first.
- `en/notebooks/*.ipynb` are generated by `uv run python en/scripts/build_notebooks.py`. Never edit them directly.
- Character limits are tripled in this edition (see the glossary), because English needs about three times as many characters as Chinese for the same feedback.
- No CJK characters may remain in `en/`, except where Chinese is itself the subject (for example, a link back to the Chinese original) and in the glossary.

## Sources and outputs

- slides/session1.html and slides/session2.html are single-file HTML slide decks. Keep the existing design, keyboard controls, and speaker notes. Each `section` has a stable id. After reordering, run scripts/sync_slide_navigation.py to rebuild each slide's static navigation and aria page numbers, and to sync the references in notebooks and docs.
- notebooks/ holds the seven course notebooks plus the optional-after-class 2-E. **Do not edit the .ipynb files directly.**
- Cell definitions live in scripts/nbspec/nb_*.py. The shared environment, saving, and generation logic is in scripts/nbbuild.py.
- review-bot/ is the instructor version of the source. writefile() generates the same program content from here.
- llm.py wraps the Colab or Gemini provider. workshop.py provides the file, record, and display helpers.
- pyproject.toml and uv.lock manage the local environment. The Colab install uses compatible version ranges. Do not call it fully pinned.

## Teaching rules

1. The main line only asks learners to operate forms, edit the specified handbook, and read output. It does not ask them to write framework code live.
2. Long infrastructure code is collapsed by default. The SKILL.md that learners edit and their homework stay visible.
3. Before an experiment, write the prerequisites and a prediction question. After it, write observation questions. Same or different output, and the model refusing or accepting, are all valid observations. Do not require re-running until a specific result appears.
4. Control experiments change one thing at a time. 2-A separates swapping the handbook, changing the body, and changing the description. In 2-B, the three versions must use the same naming rule, the same input, and the same baseline set.
5. Keep the raw tool result, the AI's final reply, and the parser-extracted value apart. A deterministic script does not guarantee that the agent calls it or relays it completely.
6. The form uses "maximum generations (including the first)". If the graph's compatible API field `max_retries` is kept, explain what it actually means (it counts generations including the first). Reaching the limit is marked "not passed". Stopping is not treated as success.
7. Valid syntax, runs successfully, and meets the assignment are three different judgments. A format check cannot verify that the content is correct.
8. Whether each Part can be re-run on its own depends on its prerequisites. Do not claim that every cell runs independently. Say whether a setup cell overwrites the handbook.
9. A browser disconnect does not mean the runtime was recycled. After a runtime is rebuilt, prepare the files again. Backing up the notebook and backing up /content/review-bot/ are different operations.
10. Put token metadata, hand-built agents, eval, RAG, deployment, and complete multi-agent systems in supplementary material, after the main line wraps up.
11. Skill, tool, MCP, workflow, and agent are not mutually exclusive categories. First decide how the rule is expressed, then decide who controls when it runs.
12. For many independent homework submissions, teach batching first, then parallelism and sub-agents. A different role name does not make verification more reliable. Use code for rules that code can check, and add human confirmation before important external actions.

## Code rules

- Use create_agent (from langchain.agents). A hand-built StateGraph + ToolNode + tools_condition is supplementary.
- Use English identifiers per [GLOSSARY.md](GLOSSARY.md) and the review-bot examples. Do not reuse the old pandas scenario.
- run_code keeps its module restrictions, timeout, and error-output limit. Never call it a full security sandbox, and never introduce eval to run arbitrary learner text.
- 2-C uses only fake-key data. The tool must not read arbitrary real environment variables. Remote shell examples are read-only and must never be executed.
- 2-D states clearly that this notebook uses the default handbook. Separate three cases: resuming an unfinished thread, retrieving the result of a finished thread, and a brand-new run on a new thread. Listing history is not Replay.
- Every notebook provides saving, a zip download, and a history printout. The closing history only reflects the cells that were run. It must not imply that all experiments are finished.

## Modifying and verifying

1. Before changing anything, check the working tree. If needed, run git pull first to get the version the instructor saved back from Colab. Do not overwrite uncommitted changes.
2. Edit scripts/nbspec and review-bot, then run `uv run python en/scripts/build_notebooks.py`. You can add a name prefix such as 1-A or 2-B.
3. Only code cells with exactly the same source keep their old output. Reordering does not carry outputs over by position, and edited code does not keep old results. Before overwriting, the generator saves the whole old notebook with stale output to notebooks/output-history/ and prints the location. If the backup fails, it stops instead of overwriting. Check the snapshot and commit the ones worth keeping. Keeping an output does not mean the new prerequisite state was verified, and blank output does not prove the user did not run the cell.
4. Run `uv run python -m unittest discover -s en/tests` to check the regression cases for semantics and output preservation.
5. Run `uv run python en/scripts/verify_notebooks.py` to run all eight notebooks from start to finish. It uses the fake model in tests/mock_colab/. This checks program flow only. It does not show real model quality or real Colab compatibility.
6. After editing the slides, run `uv run python en/scripts/sync_slide_navigation.py --check` to check that page numbers, in-text references, and the outline agree.
7. Before class, do a separate trial run of the main operations on real Colab. Confirm which features the account has, the model quota, and the actual time each part takes.
