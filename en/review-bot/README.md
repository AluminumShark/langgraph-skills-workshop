# review-bot: the Homework Helper (instructor source code)

This folder is the source code of the example project, the Homework Helper. When you run the notebooks on Colab, the code writes these files to `/content/review-bot/`,
and **the content is exactly the same as here**: the `%%writefile` cells are generated by reading the files straight from this folder (see `en/scripts/build_notebooks.py`).

## What each file is, and which notebook writes it

| File | What it is | Written by which notebook |
| --- | --- | --- |
| `graph.py` | The 1-A workflow: `check_syntax → give_feedback → check_format`. A syntax error branches to `explain_error`, and feedback that fails the format check is sent back for a rewrite, up to the limit | 1-A (`%%writefile`); 2-D uses it too |
| `agent.py` | The 1-B agent: the one-line `create_agent` version, the expanded version built by hand with `StateGraph(MessagesState) + ToolNode + tools_condition`, and `pretty_trace` | 1-B (`%%writefile`) |
| `tools/run_code.py` | Runs the homework under teaching restrictions (not a full security sandbox): blocks `import os/sys/subprocess/shutil`, adds a timeout to the child process, and squeezes errors into one line | 1-B (`%%writefile`); 1-0 and others write it too |
| `tools/check_indent.py` | Checks indentation and line length (deliberately leaves naming alone, which is saved for 2-B) | 1-B (`%%writefile`) |
| `tools/read_spec.py` | Reads the assignment requirements (`spec.md`) | 1-B (`%%writefile`) |
| `tools/check_naming.py` | Wraps the Skill's script `check_naming.py` as an agent tool | 2-B; 2-D uses it too |
| `spec.md` | The assignment requirements; the 1-B form rewrites it when you change the assignment | 1-B and others |
| `my_homework.py` | Lets students paste their own homework; the form reads it when you choose "My homework" | 1-A, 1-B (`%%writefile`, optional) |
| `skill_loader.py` | Reads only the "card" (name, description) of each SKILL.md so the model can pick one, then reads the body | 2-A (`%%writefile`); 2-D uses it too |
| `skills/friendly-feedback/SKILL.md` | Handbook: gentle and encouraging | 2-A (`%%writefile`) |
| `skills/strict-review/SKILL.md` | Handbook: strict review | 2-A (`%%writefile`) |
| `skills/naming-check/SKILL.md` | Handbook: naming check (placement B: tell the AI to run a script) | 2-B (`%%writefile`) |
| `skills/naming-check/SKILL.version-a.md` | Placement A of the naming check (the rules written in the handbook text); 2-B uses a different file name from version B so they don't overwrite each other | 2-B (`%%writefile`) |
| `skills/naming-check/scripts/check_naming.py` | Script: checks whether variable and function names are lowercase with underscores; the same input and script version give the same result | 2-B (`%%writefile`) |
| `skills/detailed-feedback/SKILL.md` | The experiment handbook for 2-C: one bad instruction is hidden in the middle (keys are always fake) | 2-C (`%%writefile`) |
| `skills/detailed-feedback/scripts/setup.sh` | The experiment script for 2-C: contains `curl ... \| bash` and an encoded string you can't read. **It is only for you to read; the notebook never runs it** | 2-C (`%%writefile`) |
| `dual_core.py` | 2-D, combining workflow and agent: the outer workflow controls branches and order, and `give_feedback` holds a small agent with a handbook and tools; each homework's assignment lives in State.spec and read_spec reads only that one; a SQLite checkpointer saves the State by `thread_id` | 2-D (`%%writefile`) |

### 2-E (optional after class): getting ready for the cloud

| File | What it is |
| --- | --- |
| `deploy/homework_mcp.py` | Exercise 1: the "homework repo" MCP server (`list_homework`, `get_homework`, `send_email`). The tools live in another program: stdio is a local socket, and `--http <port>` turns it into a URL (Streamable HTTP, like a remote MCP). Sending email is fake and only writes to `outbox.txt`. 1-B Part 6 uses it too, but hands only the read tools to the agent |
| `deploy/multi_agent.py` | Exercise 2: run the whole division-of-labor diagram once: MCP fetches homework → code checks syntax → `Send` starts review sub-agents (handbook + the `check_naming` script + `run_code`) → verification agent (auditor + code check of line numbers) → `interrupt()` waits for a person to confirm → MCP sends email |
| `deploy/server.py` | Exercise 3: wraps the multi-agent Homework Helper as an API service with FastAPI (`GET /health`, `POST /batch`, `POST /batch/{thread_id}/decision`, `GET /threads/{thread_id}`) |
| `deploy/preflight.py` | Exercise 4: pre-launch checks (hard-coded keys, third-party Skill scan, run_code fence, recursion_limit, checkpointer, interrupt before sending email, deployment files) |
| `deploy/app_graph.py` | Exercise 4: the entry point that `langgraph.json` points to; the model provider, the key and the MCP server URL are all read from environment variables |
| `langgraph.json` | The packing slip: tells `langgraph dev` / LangSmith Deployment "where the graph is" |
| `requirements.txt`, `Dockerfile`, `.dockerignore` | Put the code, `skills/` and `scripts/` into one container; keys do not go into the image and are injected by the cloud's Secret Manager |
| `.env.example` | A template of environment variables for local use (copy it to `.env`; `.env` stays out of git) |

All of these are written by 2-E with `%%writefile`. 2-E only creates files and practices inside Colab; it does not really deploy anything.

## Workshop infrastructure (students don't need to read this)

| File | What it is |
| --- | --- |
| `llm.py` | The model adapter: wraps Colab's built-in model `google.colab.ai` (the default, no API key needed) or the instructor's Gemini key into the same `model`. This course's Colab adapter writes the tool descriptions into the prompt, asks the model to reply with JSON, and turns that into `tool_calls` in the same format |
| `workshop.py` | Small helpers shared by the notebooks: `prepare()` at the start of each part, the sample homework, saving the results that experiment cells name, drawing the graph, saving to Google Drive, and downloading a zip |

These two files are written by the first cell of every notebook, "0. Environment setup".

## Files that only appear at run time (not in the repo)

- `history.jsonl`: the results that experiment cells chose to save; the last cell, "📸 Print the recorded experiment results", reads it. It is not every intermediate state
- `checkpoints.sqlite`: the 2-D checkpoint (an unfinished thread can be continued; a finished one gives back its result; a new ID starts a new run)
- `.llm.json`: remembers which model provider you chose (the API key is not saved)
- `outbox.txt`, `deploy/multi_agent.sqlite`, `deploy/.port`, `deploy/.mcp_port`: created during the 2-E exercises (1-B Part 6 uses only the homework-reading tools)
