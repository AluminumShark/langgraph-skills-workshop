# 課綱：從 LangGraph 到 Skills

兩堂各 120 分鐘，對象是看得懂 Python 的 dict、函式、if、while 的初學者。課堂以「預測 → 執行 → 對照 → 說出原因」為主，不要求現場寫框架程式。

## 共同學習目標

用同一個「作業小助教」串起兩堂課。學生最後應能：

1. 區分模型回覆、工具請求、程式實際執行，以及把結果交回模型的迴圈。
2. 追蹤 workflow 的 State、節點與條件分支，分清「通過檢查」和「達到次數上限而停止」。
3. 固定作業，一次只改需求、手冊正文或 description 中的一項，觀察 Skill 如何影響選擇與回覆。
4. 分別決定「規則放在哪裡」和「誰決定何時執行」，不把 Skill、tool、流程節點當成互斥選項。
5. 指出惡意手冊要求了什麼、需要哪個工具權限，以及權限拿掉後少了哪種能力。
6. 區分未完成 checkpoint 的續跑、已完成結果的取回，以及新 thread 的全新執行。

「語法正確」「執行成功」「符合題目要求」是三個不同判斷。這個課程範例不會因為語法檢查通過，就宣稱作業正確。

### 1-0：先看到交接，才談自動化

- 主線先看模型的回答，再看工具請求，再由程式執行工具、回傳結果。
- 模型沒有呼叫工具也是有效觀察，不能靠重跑到「想要的結果」才算成功。
- context 用可見的對話訊息解釋；模型不會自動讀到本機檔案或之前沒傳入的對話。
- token／response metadata 放補充；實測數值與估算值分開。
- 手組迴圈的細節不作為初學者必背內容。

### 1-A：先懂一次狀態變化，再看重做

先讀輸入與預期輸出，再看節點前後的 State。先預測語法錯誤會走哪一條路，之後才看格式檢查的退回。

「最多生成次數」包含第一次生成。程式內相容欄位仍可能叫「最多重試次數」，但課堂表單及解釋不可把它說成額外重試次數。檢查標記與字數只是格式檢查，不能驗證回饋內容正確。

最低完成：用一份語法有錯的作業與一份可通過語法的作業，指出路線差異；再分辨成功停止和達到上限停止。

### 1-B：先理解工具，再接外部工具

主線先直接測試工具，再看工具說明、建立 agent、觀察路線與執行上限，最後示範 MCP 交接。重複執行時，路線相同或不同都有效；請記錄實際觀察，不要求一定出現變化。

MCP 是連接工具與資料的協定。直接使用 API 也是選項；MCP 不代表模型能直接看到工具實作，也不保證省下所有工具說明的 context。程式提供什麼工具，agent 才能使用什麼能力。

手組 StateGraph、完整程式碼對照移到補充，不打斷第一次操作的主線。

### 2-A：三個實驗一次只改一項

1. **A：固定作業與兩本預設手冊，只改需求。** 先看選中的手冊，再觀察回饋，建立需求、名片與手冊的關係。
2. **B：固定選 friendly 手冊與初學者需求，只改一條可觀察的結尾規則。** 修改後執行寫檔格；比較修改前後，不同時更換需求。
3. **C：恢復預設內容，固定需求，只改 description。** 觀察選到的手冊，與正文內容的效果分開。

先選一本、再讀正文是本課程 loader 的行為，不是模型天生會掃描資料夾。選擇失敗應可見，不應悄悄改選第一本造成誤判。

### 2-B：比較同一個規則的可靠度

命名規則的範圍、常數例外與預期名稱集合，三版一致。先讓學生看作業、找出可疑名稱，再揭露基準答案。

| 版本 | 規則如何表達 | 誰決定執行 | 需要觀察 |
| --- | --- | --- | --- |
| A | 手冊文字 | 程式請模型解讀與判斷 | 回覆列出的名稱；三次相同也可接受 |
| B | 同一規則寫成腳本，手冊說明使用方式 | agent 決定是否呼叫工具 | 是否呼叫、工具原始結果、最終回覆 |
| C | 同一支檢查程式直接放入流程 | 程式固定執行 | 原始檢查結果是否一致 |

腳本的確定性只涵蓋同樣輸入下的腳本輸出；不保證 agent 一定呼叫，也不保證 AI 完整轉述。從自然語言解析出的名稱另列，不能拿解析器的結果冒充原始工具結果。

A/B 使用不同手冊檔，避免後一個實驗覆寫前一個。重跑時先執行該版本的準備格。

### 2-C：固定手冊，改變可用能力

主線限制在 10 分鐘：先預測，再用同一本手冊比較有／無 read_env 工具，依紀錄找出惡意行。工具只讀練習用假資料，不讀真實環境中的任意變數，也不執行手冊中的遠端 shell 指令。

模型拒絕惡意要求是可接受結果。不要反覆重跑到外洩才宣布實驗成功；需要理解的是能力與權限邊界。靜態掃描、安裝腳本分析放補充。關鍵節點與人工確認不應只寫成「請 AI 記得」。

### 2-D：先完成一次，再看存檔

預留 15 分鐘。這本使用明示的預設手冊，不會自動沿用另一個 Colab runtime 中修改過的檔案。

| 狀態 | 操作與結果 | 學生要說出的差別 |
| --- | --- | --- |
| 同一 thread，尚有下一步 | 從 checkpoint 繼續剩餘工作 | 接著做 |
| 同一 thread，已完成 | 取回保存的結果，不把它叫重新跑 | 拿回結果 |
| 新 thread | 從新的初始輸入開始 | 新的一次 |

列出歷史 checkpoint 是歷程檢視，不能直接稱為 Replay。真正重跑特定 checkpoint 是另一種操作。純 agent 對照和重複評估留作選做，不在主線同時塞進多個新概念。

## 系統設計：先問兩件事

**第一件：規則或知識怎麼表達？** 可以是 Skill 文字、規格資料或可執行腳本。
**第二件：誰決定何時執行？** 可以由固定流程呼叫，也可以讓 agent 選擇。

同一支腳本能包成 tool；同一個 tool 可透過 MCP 連接；Skill 可教 agent 使用它；workflow 可把它安排在適用分支的必經節點。這些角色可以組合，不是互斥的分類；執行時仍須處理工具失敗與中斷。

設計順序：

1. 找出不能漏掉的檢查與人工確認，先放入程式流程。
2. 把可用固定程式回答的問題做成可測試的工具。
3. 把語氣、步驟指引與情境判斷寫成手冊。
4. 確認剩下哪些選擇需要 agent，並限制工具權限與執行上限。
5. 外部服務需要共用介面時，再考慮 MCP；並非所有外部呼叫都要 MCP。
6. 多份獨立作業先考慮批次執行；有可拆任務、上下文或權限需求時，再考慮子 agent。

「多個角色名字」本身不會讓審查可靠。驗證者需要清楚的通過標準與可核對的證據；能寫成程式的規則先由程式驗證，無法自動決定且影響重要的動作交給人工確認。

### 設計單

請為自己的作業小助教填出：輸入／輸出、必做檢查、工具、手冊內容、agent 可決定的事、停止條件、失敗處理，以及需要人工確認的動作。先畫最小可工作的版本，再解釋是否需要第二個 agent。

| 1-B | 記錄工具路線，理解 MCP 交接 | 手組 agent |
| 2-A | 一次只改一項，記錄手冊實驗 | 自訂更完整的 Skill |
| 2-B | 對照同規則的三種執行方式 | 增加案例，不預設模型一定出錯 |
| 2-C | 找惡意行並比較工具權限 | 靜態掃描與安裝腳本閱讀 |
| 2-D | 區分未完成／已完成／新 thread | 純 agent 對照與 eval |
| 2-E | 課後延伸 | MCP、批次與分工、API、部署前檢查 |

時間不足時，2-B 可由講師示範，再由學生讀紀錄回答；仍保留 2-C 的權限對照及 2-D 的三種狀態辨識。不要為了趕進階補充而跳過主線的完成檢查。

2-E 先跑一份作業確認管線，再跑多份比較批次與並行。並行上限主要影響同時執行數；延遲、重試與模型呼叫可能改變 token 用量，不給固定倍數保證。API 練習依其前置準備操作，檔案產生不等於已部署服務。

RAG、正式部署、重複 eval、完整多 agent 系統、production checklist 放在主線收束後的補充頁。課堂只標出位置，不逐一實作。

## 教材實作與驗證規範

- Notebook 來源是 scripts/nbspec/ 與 review-bot/；不要直接編輯產生的 ipynb。
- 大段基礎設施預設收合；要改的手冊與作業保留可見。每個主線實驗有前置說明、預測題與觀察點。
- 修改 SKILL.md 後必須執行寫檔格；重跑準備格可能覆寫修改，需明示。
- 每段能否獨立重跑依其前置條件而定，不作一律獨立的承諾。runtime 被回收後重做環境與檔案準備；瀏覽器斷線不等於檔案立即消失。
- 重新產生只沿用來源完全相同程式格的舊輸出；舊輸出不是本次真實模型驗證證據。
- 本機用假模型跑八本 notebook 驗流程，真實模型品質、Colab 連線和課堂耗時另做課前試跑。
- 投影片重排後執行 scripts/sync_slide_navigation.py，同步逐頁大綱、notebook 的頁碼及 README。
