## Notebook 對齊與講授注意事項

- **2-A：控制單一變因。** 第 1 段認識手冊；第 2 段實驗 A 只換需求，實驗 B 固定初學者需求與 description，由程式指定 friendly-feedback，只改一條結尾規則「下一步：請再測試一次」；實驗 C 時間許可再做，由程式恢復原始內文後只交換 description。每次顯示目前需求、選中的手冊與生效規則。實驗 B 不重新選書；先觀察修改內文的結果，再解釋名片如何影響選書。若模型沒有遵守新規則也照實記錄。各文字格會覆寫同一路徑的手冊，需確認本次載入內容。token 數與官方 Skill 下載留選做。
- **2-B：先預測再看答案。** 共用命名規則與作業，先看變數／函式／參數，數字允許，常數不豁免。A 由程式直接呼叫模型（沒有工具選擇），記錄實際結果，不重跑到不同；B 分開檢查是否呼叫、腳本結果、最後轉述；C 使用同一腳本。輸出解析失敗與檢查錯誤分開記錄。三次相同也不代表一般可靠性。第 6 段題目「最多生成三次」包含第一次，避免把生成與重寫混為一談。
- **2-B：兩個決策。** 如何完成：固定規則可用程式／腳本，判斷準則寫手冊。誰控制執行：必做放流程，按需可給 agent 工具。練習允許不同條件下有不同答案，不把程式、手冊、腳本教成互斥分類。
- **2-C：預測 → 權限比較 → 定位。** 第 1 段先認識手冊與預測，第 2 段比較同一份手冊在有／無 read_env 的行為，第 3 段再由工具紀錄與回覆找出可疑指令，只使用假的示範金鑰。未發生洩漏也記錄，不當作安全證明；無權限時猜出文字不等於讀到資料。腳本、編碼與掃描器為選做。
- **2-D：接點與輸出。** 先觀察 skill_loader、內層工具呼叫與外層格式檢查；預設手冊不是自動接續 2-A 修改。語法錯誤回報語法；正常回饋要求優點／改進；最多生成次數包含第一次；達上限仍不合格時回報未通過，不能當成成功。先以語法正確的預設作業完成整合，再試錯誤分支。
- **2-D：存檔三狀態。** 同一未完成 ID 才接續；從未使用的新 ID 加新輸入才從頭開始；已完成 ID 查看的是完成狀態。觀看歷史不是歷史重跑，後者留選讀。第 3–4 段完成三種狀態，第 5 段查看歷史；最低完成標準是能說明這三種狀態與已執行步驟。重新做實驗先依 notebook 指引重建暫停狀態，不沿用已完成 ID。
- **2-D eval：課後選做，架構切換要說清楚。** 對比的是純 agent 的 baseline／提示修改，不是主線的流程與 Agent 整合架構。評分不另叫模型，被測 agent 仍用模型。五題的通過率只代表該次測試；流程仍要測試路由、格式與內容。
- **系統設計：角色可以搭配。** Tool 是操作能力，MCP 是一種連接方式，Skill 是做法準則，流程是控制。Skill 不會自動隱藏 MCP 工具 schema。先討論同一 agent 使用每份獨立輸入，再按速度需求有限並行；子 agent 要有上下文、權限或獨立判斷理由，不只是不同語氣。
- **驗證：先固定規則，再必要的語意審查。** 驗證者需要題目、作業原文與回饋草稿，不能只給孤立答案。它也可能判錯。寄信確認需是流程必經節點，避免另一條工具路徑繞過。
- **收束順序固定。** 完整分工圖 → 六個決策問題 → 學生任務 → 兩堂總結。RAG、eval、production 清單與部署全部移至總結後的選讀，不再追加課堂講解。
- **2-E：成果階段分開。** Colab 模擬工具與人工確認、本機 API、產生部署檔、實際建置部署是不同完成階段。產生 Dockerfile 或 langgraph.json 不等於公開上線；課堂不寄真信。

## 授課方式

學生只需既有 Python 基礎：變數、函式、字典、if 與迴圈。核心活動以執行預備儲存格、改需求／文字與觀察紀錄為主；API 實作細節與雲端配置不作先備要求。每個觀察先請學生預測，再看結果；不要要求模型一定演出預設失敗。原投影片的來源編號保留於 HTML 參考資料頁，外部服務規格與價格以實際使用時的官方文件為準。
