為什麼要有名片：先選手冊，再讀內容

50 本手冊，這個載入器不會把全文全攤在桌上（桌子 ＝ AI 一次讀得下的內容上限，上週講過）。它先看每本的名片，決定要翻哪一本，翻開才讀內容 [1]。

description 這樣寫AI 會怎樣
「幫忙處理回饋」不知道什麼時候該翻，較難判斷是否適用
「給 Python 初學者的作業回饋。語氣溫和，先講優點再講改進。」較容易對應初學者回饋需求
名片會影響選書；實際選擇仍受需求與模型判斷影響。

想像你有 50 本手冊。這個載入器不會把 50 本全文全攤在桌上（還記得上週的桌子有多大嗎），它先看每本的名片，決定要翻哪一本，翻開才讀內容 [1]。所以名片會影響選書；實際選擇仍受需求與模型判斷影響。

分工圖搬上雲端：每一格住在哪裡

細節在「補充：上雲端」（投影片 48–56）課後練習Colab 2-E 練習 1–2 用模擬倉庫與寄信工具跑分工流程；練習 3–4 準備 API 與部署檔

程式、手冊、腳本跟著容器走；會變的資料進資料庫；鑰匙進保管箱；別人的能力透過網路接進來。

課後選讀的部署概念圖；先完成核心練習，再依需要閱讀部署細節。

把完整分工圖搬上雲端，每一格會住在不同的地方。中間是「你的容器」：API（別人用網址把作業送進來）、外層流程（程式）、回饋 agent、本地 tool，還有 skills/ 和 scripts/，它們跟程式一起打包進映像，部署時需核對程式、手冊與附件版本。容器可以放在 Cloud Run 這類服務，或交給 LangSmith Deployment 代管。

會變的資料不放在容器裡，因為雲端執行個體可能重啟或更換：每個 thread_id 的 State、等人按確認的信、RAG 要查的向量資料，都放進資料庫（例如 Postgres）。模型的 API key 和 OAuth token 放進保管箱（Secret Manager），部署時才變成環境變數。

別人的能力透過網路接進來：模型本身是別人的 API；從 GitHub 抓作業、寄信是遠端 MCP；run_code 要跑學生寫的程式，上線後一定丟進沙箱。旁邊還有任務佇列（200 份排隊）和 Trace／Eval 儀表板（看得見每一步、改了就自動考試）。

200 份同時批：Send

from langgraph.types import Send def 分派(state):    # 每份作業傳入獨立資料，執行同一節點    return [Send("批一份", {"code": c}) for c in state["作業們"]] builder.add_conditional_edges("抓作業", 分派, ["批一份"]) # 一次最多 20 份同時跑，其餘排隊graph.invoke(輸入, config={"max_concurrency": 20})

結果用 Annotated[list, operator.add] 的欄位收回來，就是 map-reduce [14]。

  • 每份一張乾淨的桌子：避免沿用前一份對話；仍需核對學生 ID 與結果對應
  • 要設並行上限：模型 API 每分鐘有上限，一次發出太多請求可能碰到配額限制
  • 先算錢：先量每份的呼叫與 token，再估計批次總量；並行不等於固定倍數成本

課後練習Colab 2-E 練習 2：Send 分派 5 份獨立作業，量測呼叫與 token

Send：在流程裡說「這個節點，照這份清單一份開一個」，LangGraph 依並行限制安排執行。

Send 分派獨立輸入到同一節點；節點可以呼叫同一套 agent，並不要求新角色。設定並行上限，保留學生 ID，量測每份與整批成本。實際速度仍受模型與資源限制。

寄信前等待確認：interrupt()

from langgraph.types import interrupt, Command def 寄信(state):    答案 = interrupt({"收件人": state["email"], "內容": state["feedback"]})    if 答案 == "寄":        send_email(state["email"], state["feedback"])   # MCP 工具    return {"已寄出": 答案 == "寄"} # 幹部在後台看過內容、按下「確認」之後：graph.invoke(Command(resume="寄"), config={"configurable": {"thread_id": "小明-期中"}})
  • interrupt 把 State 存進 checkpointer 然後停住，等待期間需要保留可恢復的存檔 [15]
  • 部署時需使用持久化的 checkpointer，並保存資料，避免重啟後遺失等待中的進度

課後練習Colab 2-E 練習 2：寄信前用 interrupt() 停下來，人確認後用 Command(resume=…) 接著跑，才記錄模擬寄信結果（課堂不寄真信）

第 38 張的「寄之前一定要有人按確認」，在這裡透過流程與存檔機制實作。

寄信不可逆，所以第四站說外面要加一道人工確認。LangGraph 的做法是 interrupt：執行到這裡會把 State 存進 checkpointer 然後停住，回傳要給人看的內容；人確認之後，用 Command(resume=...) 帶著同一個 thread_id 叫它繼續，resume 的值就是 interrupt 的回傳值 [15]。

這也是為什麼雲端要用持久的 checkpointer：幹部可能三天後才按確認，等待期間執行個體可能已更換。官方文件也建議 production 用 durable checkpointer [15]。

上線之後：看得見、關得住

看得見（行動後檢查）
  • Trace：每一份作業的每一步都留紀錄，出錯時查得到是哪一步
  • Eval 進 CI：第 44–45 張的五個案例，每次改手冊或程式都自動跑，依團隊門檻判定是否接受改動
  • 成本：每份作業花多少 token，每天看一次
關得住（權限與習慣）
  • 每個工具只給需要的權限：寄信的 agent 拿不到刪檔的工具
  • run_code 在隔離環境執行：限時、限記憶體、不能連網
  • 第三方 Skill 進 repo 前，照 2-C 的三個習慣審過，並鎖定版本
  • 金鑰只放 Secret Manager，絕不寫進 SKILL.md、程式或 git
  • 本例在寄信前用 interrupt 等待人工確認

上雲端不是換個地方跑，是補齊部署與維護的工作：保留必要的執行紀錄，每個工具權限明確可控。

右邊是權限：最小權限、沙箱、審查第三方 Skill、金鑰放 Secret Manager、不可逆的動作前面要有人確認。2-C 的實驗在雲端更危險，因為部署後的系統可能獲得真實憑證與信箱權限。
